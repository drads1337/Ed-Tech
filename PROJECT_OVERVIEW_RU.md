# Объяснение проекта Ed-Tech

## Короткая суть

Этот проект я понял как прототип ed-tech платформы для тренировки профессиональных диалогов через AI-ролевые сценарии и 3D-визуализацию.

Главная идея такая: компания или отдельный пользователь загружает учебный материал, например FAQ, скрипт продаж, SOP или инструкцию. На основе этого материала система генерирует тренировочный сценарий. Сотрудник проходит симуляцию диалога с AI-персонажем, получает оценку, обратную связь и прогресс. Администратор видит результаты команды в дашборде.

Базовая продуктовая цепочка:

```text
учебный материал -> AI-сценарий -> назначение сотруднику -> попытка -> оценка -> дашборд
```

То есть это не просто 3D-сцена и не просто LMS. По смыслу это тренажер коммуникаций: продажи, поддержка, медицина, право, образование, экстренные службы и другие сферы, где важно уметь отвечать правильно, спокойно и по протоколу.

## Что уже есть в проекте

Проект состоит из двух больших частей:

1. Фронтенд на React/Vite.
2. Бэкенд на FastAPI с Supabase-хранилищем или in-memory demo-режимом.

Фронтенд сейчас выглядит как демо-приложение с регистрацией, онбордингом, личным кабинетом и подготовленной 3D-сценой. Бэкенд уже описывает основной API для будущего полноценного сценария: материалы, сценарии, назначения, симуляция, попытки и дашборды.

## Фронтенд

Главный frontend-файл: `src/App.jsx`.

Роуты приложения:

```text
/signin      - вход
/signup      - регистрация
/onboarding  - настройка пользователя
/dashboard   - кабинет пользователя или администратора
```

### Регистрация и вход

Регистрация сделана в демо-режиме через `localStorage`. Пользователь выбирает тип аккаунта:

- `solo` - индивидуальный пользователь;
- `admin` - координатор обучения компании;
- `employee` - сотрудник по приглашению.

Настоящий Supabase-клиент уже есть в `src/backendApi.js`, но текущий пользовательский путь во фронтенде в основном работает локально, без реального запроса к API.

### Онбординг

После регистрации пользователь проходит 5 шагов:

1. Выбор сферы.
2. Выбор роли.
3. Выбор цели.
4. Выбор режима/уровня тренировки.
5. Подтверждение того, как система поняла пользователя.

Онбординг нужен, чтобы тренировки в будущем были персональными: например, продавец тренирует возражения, врач тренирует объяснение пациенту, преподаватель тренирует вовлечение ученика.

### Дашборд

Дашборд строится из mock-данных в `src/mockData.js`.

Для администратора показываются:

- организация;
- количество сценариев;
- слабые навыки;
- completion rate;
- средний score;
- назначенные сотрудники.

Для сотрудника показываются:

- назначенные тренировки;
- статус;
- требуемый score;
- карточки сценариев.

Кнопка `Start training` сейчас визуально есть, но в текущем роутинге она еще не соединена с полноценным экраном тренировки.

## 3D-сцена

В проекте есть сильная 3D-часть на Three.js, React Three Fiber и Drei.

Используются модели:

- `ordinary.glb` - сцена с лежанкой;
- `bearded.glb` - персонаж стоя;
- `note.glb` - персонаж сидя;
- `table.glb` - рабочий стол;
- также есть `bearded.glb`, `table.glb`, `note.glb` и другие GLB-ассеты в корне проекта.

Основная логика 3D-сцены находится в `src/App.jsx`, а настройки поз - в `src/casePoses.js`.

Доступные кейсы:

```text
Лежанка
Стоя
Сидя
Рабочий стол
```

Для каждого кейса есть:

- модель;
- позиция камеры;
- трансформации модели;
- повороты костей персонажа;
- окружение;
- свет;
- декоративные линии Aurora.

Сцена реализована как компонент `SimulationScene`, но сейчас он не подключен к маршрутам приложения. По смыслу именно эта сцена должна стать визуальной частью тренировки, где пользователь видит персонажа/обстановку во время симуляции.

## Бэкенд

Бэкенд находится в папке `backend/`.

Основной файл запуска: `backend/app/main.py`.

Фреймворк: FastAPI.

Смысл бэкенда - обслуживать полный цикл тренировки:

```text
POST /api/materials
POST /api/scenarios/generate
POST /api/assignments
GET  /api/employee/dashboard
POST /api/simulation/message
POST /api/attempts/evaluate
GET  /api/admin/dashboard
```

### Основные сущности

Модели описаны в `backend/app/schemas.py`:

- `Profile` - пользователь;
- `TrainingMaterial` - учебный материал;
- `Scenario` - AI-сценарий;
- `Assignment` - назначение сотруднику;
- `TranscriptMessage` - сообщение в диалоге;
- `Attempt` - попытка прохождения;
- `EmployeeDashboard` - кабинет сотрудника;
- `AdminDashboard` - кабинет администратора.

### Хранилище

Репозитории находятся в `backend/app/repositories.py`.

Есть два режима:

- `SupabaseRepository` - реальная работа через Supabase;
- `InMemoryRepository` - demo-режим в памяти, если Supabase-настройки не заданы.

Supabase-схема лежит здесь:

```text
backend/supabase/schema.sql
```

Там создаются таблицы:

- `organizations`;
- `profiles`;
- `training_materials`;
- `scenarios`;
- `assignments`;
- `assignment_employees`;
- `attempts`.

Также есть seed-файл для демо-пользователей:

```text
backend/supabase/seed_demo_profiles.sql
```

### AI-логика

AI сейчас замокан в `backend/app/services/mock_ai.py`.

Там есть три ключевые функции:

- `generate_scenario()` - создает сценарий из материала;
- `continue_roleplay()` - продолжает ролевой диалог;
- `evaluate_attempt()` - оценивает попытку и возвращает score, skill scores и feedback.

Это пока не настоящая LLM-интеграция, а детерминированная заглушка для проверки продуктового цикла.

## Как я понимаю пользовательский сценарий

Идеальный сценарий продукта должен выглядеть так:

1. Админ регистрирует организацию.
2. Админ добавляет учебный материал.
3. Система генерирует AI-сценарий.
4. Админ назначает сценарий сотрудникам.
5. Сотрудник открывает кабинет и видит тренировку.
6. Сотрудник запускает симуляцию.
7. AI-персонаж задает вопрос или возражение.
8. Сотрудник отвечает.
9. AI продолжает диалог.
10. После завершения система оценивает попытку.
11. Сотрудник получает feedback.
12. Админ видит score, completion rate и слабые навыки команды.

## Текущее состояние

Что выглядит уже готовым или почти готовым:

- React-приложение с регистрацией, онбордингом и дашбордом.
- 3D-сцена с несколькими кейсами и GLB-моделями.
- FastAPI-приложение с основными endpoint-ами.
- Supabase-схема для ключевых таблиц.
- In-memory demo-режим для тестов и запуска без Supabase.
- Pytest-тесты полного backend demo flow.
- Скрипт проверки поз `npm run check:pose`.

Что пока выглядит как незавершенная стыковка:

- фронтенд-дэшборд не использует backend API в основном пользовательском пути;
- `SimulationScene` определен, но не подключен к роутингу;
- кнопка `Start training` пока не запускает симуляцию;
- mock AI нужно заменить или дополнить настоящей AI-интеграцией;
- README местами говорит, что бэкенда нет, хотя папка `backend/` уже содержит рабочий MVP-каркас.

## Архитектура простыми словами

```text
React UI
  |
  |-- auth/register/onboarding в localStorage для демо
  |-- dashboard из mockData
  |-- 3D scene через React Three Fiber
  |
FastAPI backend
  |
  |-- принимает материалы
  |-- генерирует сценарии
  |-- назначает тренировки

  |-- собирает dashboard data
  |
Supabase или InMemoryRepository
  |
  |-- users/profiles
  |-- organizations
  |-- materials
  |-- scenarios
  |-- assignments
  |-- attempts
```

## Главная ценность проекта

Ценность проекта в том, что он превращает обучение из пассивного чтения материала в практику.

Пользователь не просто читает инструкцию. Он попадает в ситуацию, отвечает живому AI-персонажу, ошибается, получает оценку и видит, какие навыки нужно улучшить. Для компании это способ быстро понять, кто готов к реальным разговорам с клиентами, пациентами, учениками или коллегами, а кому нужно еще потренироваться.

Если довести проект до цельного состояния, это может стать платформой для AI roleplay training с визуальной 3D-оболочкой, персональным онбордингом, командными назначениями и аналитикой качества коммуникации.
